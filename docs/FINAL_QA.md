## 3. RT-10 · CRITICAL · Дефект A-08 не был устранён (найден благодаря RT-01)

**REPRODUCE.** Первый же запуск исполнителя провалил `GT-B3-04` — регрессионный случай дефекта A-08.

**ROOT CAUSE.** В `computeFourPillars` столпы года и месяца выводились из `norm.jdUTC` (единая шкала), а столпы дня и часа — из **сырых локальных чисел** `input.{year,month,day,hour}`. Это прямое нарушение правил TZ-3 и TZ-4 спецификации: «ВСЕ четыре столпа определяются из ОДНОГО instantJD».

Практическое следствие: поправка истинного солнечного времени сдвигала момент и меняла год/месяц, но **не могла** изменить день и час — даже если пересекала полночь.

**FIX.** Реализовано правило TZ-4: локальная гражданская дата восстанавливается из единого момента (`localJD = instantJD + tz/24`), и столп дня берётся уже по ней.

**RUN.**
```
без поправки истинного солнечного времени: день 0/10, час 0/0
с поправкой (долгота 60°, пояс +3)       : день 1/11, час 2/0
```
Раньше обе строки совпадали.

**TEST.** `GT-B3-04` проходит; добавлен интеграционный тест «Единая шкала времени».

**REGRESSION TEST.** Три эталонных профиля (1967 MSK, 2024 UTC+0, 2025 у Ли Чунь) — столпы **идентичны** значениям до правки.

### Отдельно: ошибочный эталон GT-B3-04

Исходная формулировка требовала, чтобы при **одинаковом локальном времени** 01:00 и поясах UTC+12 / UTC−12 столпы дня различались. Это требование **невыполнимо ни при какой корректной реализации**: столп дня определяется местной гражданской датой (правило TZ-4), а она в обоих случаях одна и та же.

Проверено внешними источниками: столп дня строится по местному времени; при этом расхождения между школами касаются границы (23:00 против 00:00) и поправки на солнечное время, а не часового пояса как такового.

Эталон **переформулирован**, а не удалён: теперь он проверяет подлинный смысл A-08 — влияние поправки истинного солнечного времени на столп дня. Причина замены зафиксирована прямо в поле `note` случая.

## 4. RT-02 · HIGH · Конфликт K4: код противоречил данным

**REPRODUCE.** `bazi.json` объявлял `lateZi` («смена дня в 00:00») режимом по умолчанию, а исполнение показывало смену дня в 23:00.

**ROOT CAUSE.** Три дефекта в одной точке: флаг `lateZiNewDay = true` включал поведение *раннего* Цзы (имя перевёрнуто); значение по умолчанию было зашито в коде; настройка `ziHourConflict.modes` из JSON **не читалась вовсе**.

**FIX.**
1. Флаг переименован в `earlyZiNewDay` — имя теперь отражает поведение.
2. `loader.js` строит `t.ziRule` из `bazi.json`; движок получает режим оттуда.
3. Все точки построения столпов принимают `zi` как параметр.

**RUN.** Режим из данных — `lateZi`, поэтому столп дня больше не меняется в 23:00:
```
22:00 -> день 9/3   23:00 -> день 9/3   00:00 -> день 9/3
```

**TEST.** Юнит-тест переименован в «Ранний час Цзы (23:00) переносит столп дня» и явно задаёт школу; `GT-B3-03` проверяет школу раннего Цзы независимо от значения по умолчанию.

**REGRESSION TEST.** Эталонные профили не изменились (рождения вне интервала 23:00–24:00 не затрагиваются).

**KNOWN LIMITATION.** Конфликт K4 остаётся **UNRESOLVED**: обе школы существуют. Проект фиксирует выбор в данных и позволяет его изменить, но не утверждает, какая школа верна. Переключатель в интерфейсе не сделан — режим меняется правкой `bazi.json`.

## 5. RT-03 · HIGH · Правило CONST-1 обходилось молча

**REPRODUCE.** `yearIndexFromSolarYear(2026)` без аргумента данных возвращал `42`, `annualStar(2026)` → `1`, `computeLuckPillars(...)` без `rules` → `startAge 1.2815`. Ни одного исключения.

**ROOT CAUSE.** Откаты вида `anchors ? anchors.yearPillar : 1984` оставляли литералы в коде. Формально ARCH-1 был «устранён», фактически данные можно было обойти незаметно, а тест на чувствительность этого не ловил, так как всегда передавал `anchors` явно.

**FIX.** Откаты удалены; отсутствие данных — ошибка:
```js
if (!anchors || typeof anchors.yearPillar !== 'number') {
  throw new Error('CONST-1: не передан якорь столпа года (calendar.json -> epochs.yearPillarAnchor)');
}
```

**RUN.** Все три функции теперь падают с внятным сообщением, указывающим нужный файл и поле.

**TEST.** Добавлен архитектурный тест «CONST-1: вызов без данных ПАДАЕТ».

**REGRESSION TEST.** Правка вскрыла **реальный необнаруженный дефект**: `computeTimeSeries` вызывал `computeLuckPillars` без `anchors`, то есть столпы удачи во временном ряде считались по зашитому якорю, а не по данным. Исправлено. Значения не изменились (литерал совпадал с данными), но зависимость стала явной.

Статус **MVP / экспериментальное приложение** сохраняется. Заявление о production-готовности было бы необоснованным: семь конфликтов источников не разрешены, формулы графиков референса неизвестны, визуальное соответствие не проверено, браузерное тестирование ведётся на заглушке.

**Не публиковалось.**
