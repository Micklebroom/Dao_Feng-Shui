## RT-02 · HIGH · Конфликт K4: код противоречит собственным данным

**EVIDENCE.**

`data/bazi.json`:
```json
"ziHourConflict": {
  "note": "Реализация по умолчанию — смена в 00:00; выбор ЯВНО декларирован, а не скрыт.",
  "modes": [ {"id":"lateZi","ru":"Смена дня в 00:00 (поздний Цзы)","default":true},
             {"id":"earlyZi","ru":"Смена дня в 23:00 (ранний Цзы)","default":false} ]
}
```

`src/engine/ganzhi.js:44`:
```js
const { lateZiNewDay = true } = opts;
if (lateZiNewDay && hour >= 23) jdn += 1;      // день меняется в 23:00
```

Исполнение подтверждает поведение кода:
```
03.06 12:00 -> столп дня 60-инд. 39
03.06 23:00 -> столп дня 60-инд. 40   ← день сменился в 23:00
04.06 12:00 -> столп дня 60-инд. 40
```

**WHY IT MATTERS.** Три отдельных дефекта в одном месте:
1. **Данные лгут.** JSON утверждает «смена в 00:00», код меняет в 23:00 — то есть фактически работает `earlyZi`, объявленный как `default: false`.
2. **Имя перевёрнуто.** Флаг `lateZiNewDay = true` включает поведение *раннего* Цзы; читающий код поймёт наоборот.
3. **Настройка недоступна.** `ziHourConflict.modes` из JSON **никогда не читается** движком (`grep` даёт совпадения только в самом JSON). Задекларированный «явный выбор» пользователю недоступен.

Последствие: для всех рождений между 23:00 и 24:00 столп дня — а через 五鼠遁 и столп часа — берутся по школе, противоположной объявленной. Это меняет Хозяина дня, то есть базовую величину всего профиля.

**REPRODUCTION.**
```bash
node --input-type=module -e "
import { loadTables } from './src/data/node-loader.js';
import { buildProfile } from './src/model/profile.js';
const T=loadTables();
for (const h of [22,23,0]) {
  const p = buildProfile({year:2025,month:6,day:3,hour:h,minute:0,gender:'male',tzOffsetHours:0},T);
  console.log(h+':00 -> день', p.pillars.day.stem+'/'+p.pillars.day.branch);
}"
```

**FIX.** Привести к одному источнику: движок обязан читать режим из `bazi.json` (`ziHourConflict.modes[].default`), а не иметь свой. Переименовать флаг в `earlyZiNewDay`, чтобы имя отражало поведение. Либо, если решено сохранить текущее поведение, — исправить JSON и объявить `earlyZi` значением по умолчанию. Конфликт K4 не разрешён, поэтому выбор обязан быть **виден и переключаем**, а не зашит.

## RT-03 · HIGH · Правило CONST-1 обходится молча: движок работает без JSON

**EVIDENCE.** Фаза 6 объявила ARCH-1 устранённым: «константы приходят из данных». Однако все точки чтения имеют молчаливый откат:
```js
ganzhi.js:62      const anchor = anchors ? anchors.yearPillar : 1984;
flyingstars.js:50 const y0 = anchors ? anchors.annualStarYear : 2024;
flyingstars.js:51 const s0 = anchors ? anchors.annualStarValue : 3;
pillars.js:125    const daysPerYear = rules ? rules.daysPerYear : 3;
pillars.js:126    const pillarYears = rules ? rules.pillarYears : 10;
```
Вызов без данных **не падает**:
```
yearIndexFromSolarYear(2026) без anchors : 42
annualStar(2026) без anchors             : 1
computeLuckPillars без rules -> startAge : 1.2815
```

**WHY IT MATTERS.** Архитектурное правило CONST-1 («ни одна доменная константа не объявляется в коде») формально нарушено: константы по-прежнему в коде, просто прикрыты условием. Если вызывающий забудет передать `anchors`, расчёт молча пойдёт по зашитым числам, а не по данным. Тест на чувствительность (`tests/architecture`) этого не ловит, потому что всегда передаёт `anchors` явно. То есть заявление «JSON управляет расчётом» верно только при дисциплине вызывающего, а не гарантировано.

**REPRODUCTION.** См. команду выше — три функции возвращают результат без единого аргумента из данных.

**FIX.** Сделать параметр обязательным: при отсутствии `anchors`/`rules` бросать `DataError`, а не подставлять литерал. Добавить в `tests/architecture` проверку, что вызов без данных **падает**.

## RT-04 · HIGH · Тест, скрывающий дефект A-08, так и не переписан

**EVIDENCE.** `tests/integration/engine.test.js`:
```js
test('Часовой пояс влияет на результат у границы суток', () => {
  const a = computeProfile({... tzOffsetHours: 12 ...}, T);
  const b = computeProfile({... tzOffsetHours: -12 ...}, T);
  assert.ok(a.pillarLabels.hour.han === b.pillarLabels.hour.han);
  assert.notEqual(a.normalization.jdUTC, b.normalization.jdUTC);   // ← единственное содержательное утверждение
});
```
Аудит фазы 2 прямо отметил этот тест как маскирующий дефект часовых поясов A-08 и потребовал переписать его в Build. Этого не сделано: тест по-прежнему утверждает лишь, что `jdUTC` различается — величина, которая различается **по определению** при разных поясах, даже если все столпы посчитаны неверно.

**WHY IT MATTERS.** Тест носит имя, обещающее проверку влияния пояса на результат, но не проверяет ни один столп. Он даёт ложную уверенность и был бы зелёным при возврате дефекта A-08. При этом сам дефект **фактически исправлен** — я проверил независимо (см. §Что выдержало атаку, п. 3), — то есть тест не ловит регрессию того, что уже починено.

**REPRODUCTION.** Внести регрессию (считать столп года по локальной дате вместо `jdUTC`) — тест останется зелёным, так как `jdUTC` по-прежнему различается.

**FIX.** Заменить утверждение на проверку у **границы сезона**, где пояс обязан менять столп года: 04.02.2025 01:00 при UTC+0 даёт солнечный год 2025, при UTC+14 — 2024. Это проверяет именно то, что заявлено в названии.

## RT-05 · MEDIUM · Единственная опубликованная формула графиков не подключена

**EVIDENCE.** F2 («Хронические» = среднее, «Острые» = максимальное отклонение от среднего) — единственный графический алгоритм со статусом **VERIFIED** и дословной цитатой автора. Функция `aggregate()` реализована в `src/model/indicators.js`, но:
```
вызовов aggregate() в коде          : 0
упоминаний chronic/acute/Хроническ  : 0 в index.html и src/ui/app.js
тестов на aggregate()               : 0
```

**WHY IT MATTERS.** Проект реализует десятки INFERRED-величин, но не даёт доступа к единственному режиму, чью формулу автор раскрыл. Это перекос приоритетов: пользователь видит модельные гипотезы и не видит подтверждённого расчёта. Одновременно это мёртвый код — реализован и не покрыт тестами.

**REPRODUCTION.** `grep -rn "aggregate" src/ | grep -v "indicators.js"` → пусто.

**FIX.** Добавить переключатель «Хронические / Острые» к графику и unit-тест на инварианты из спецификации (`chronic([a]) == a`; `acute` константного ряда = та же константа; `acute` возвращает элемент исходного ряда).

## RT-07 · MEDIUM · Полярность 子 различается между таблицами без объяснения

**EVIDENCE.**
```
mountains24.json  «zi»: polarity = "yin"   (index 1, код N2)
stems_branches.json «zi»: polarity = "yang" (index 0)
```
Всего сущностей, определённых более чем в одном файле: **21**.

**WHY IT MATTERS.** С виду это прямое противоречие в данных — ровно то, что запрещено правилами фазы 4. **Проверка внешним источником показала, что противоречия нет**: chinesemetasoft.com приводит для 子 одновременно «Polarity: Yang», «Polarity San Yuan: Yin», «Polarity San He: Yang» — то есть 24 горы используют полярность школы Сань Юань, отличную от полярности земной ветви. Риск в том, что следующий разработчик (или валидатор) увидит расхождение, сочтёт его дефектом и «исправит», сломав расчёт летящих звёзд, где полярность горы определяет направление полёта.

```bash
console.log(require('./data/stems_branches.json').branches.find(x=>x.id==='zi').polarity);"
```

**FIX.** Не менять значения. Добавить в `mountains24.json` поле-пояснение: полярность здесь — Сань Юань для определения направления полёта звёзд, она намеренно отличается от полярности ветви. Добавить в `validate-json.js` проверку, закрепляющую это различие как ожидаемое (иначе кто-нибудь «выровняет» их).

## Вердикт

**Приложение нельзя считать надёжным MVP по одной решающей причине: система доказательств корректности не работает.**

Расчётное ядро в проверенной части верно, график честен, подделок нет. Но 74 эталонных случая, которыми проект обосновывает свою корректность, **никогда не исполняются** (RT-01), один заявленный конфликт разрешён в коде противоположно объявленному в данных (RT-02), правило CONST-1 обходится молчаливыми откатами (RT-03), а тест, который должен ловить возврат критического дефекта A-08, не проверяет ничего содержательного (RT-04).

Иными словами: **сегодня расчёт корректен, но проект не располагает автоматическим средством это доказать и удержать.** До устранения RT-01…RT-04 зелёный конвейер не является свидетельством правильности вычислений.

Статус **MVP / экспериментальный** подтверждаю как единственно допустимый. Заявление о production-готовности было бы необоснованным.
